# Подготовка к КР

## 1. Когда я выберу rebase, а когда merge? Почему?

**Rebase** я выберу, когда работаю в личной feature-ветке и хочу перед push в main
привести историю к линейному виду. Rebase делает `git log` чистым и читаемым,
убирает лишние merge-коммиты, упрощает ревью и `git bisect`.

**Merge** я выберу, когда:
- ветка уже опубликована (push в origin) и с ней работают другие;
- нужно сохранить полную историю разработки (например, для аудита);
- вливается большая feature-ветка с долгой историей.

**Золотое правило:** никогда не делай rebase публичных веток. Если ветка шарится
между разработчиками — только merge.

## 2. Что произойдёт, если сделать rebase публичной ветки?

Rebase переписывает историю: все коммиты получают новые хеши (D → D', E → E').
Если ветка уже запушена, локальная и удалённая истории разойдутся.

Чтобы запушить результат, придётся сделать `git push --force`. Это приведёт к тому, что:
- у коллег локальные копии разойдутся с удалённой;
- их `git pull` создаст merge-конфликты или (при `--force` со стороны коллеги) затрёт их работу;
- ссылки на старые коммиты в PR, issue, CI-логах перестанут работать;
- возможна потеря чужих коммитов, если кто-то уже успел запушить что-то поверх.

Именно поэтому существует правило: **never rebase public branches**.

## 3. Зачем нужен multi-remote и в каких реальных сценариях применяется?

Multi-remote — это работа с несколькими удалёнными репозиториями из одной
локальной копии. Реальные сценарии:

1. **Fork + upstream** (OpenSource): `origin` — мой форк, `upstream` — оригинал.
   Пушу в origin, pull request — в upstream.
2. **Зеркалирование**: основной репозиторий на GitHub, бэкап-зеркало на GitLab.
   Настраиваю `git remote set-url --add --push origin <gitlab-url>`, чтобы одним
   `git push` отправлять в оба.
3. **Миграция**: код переезжает с GitLab на GitHub, но нужно поддерживать оба
   какое-то время.
4. **Разные команды**: одна команда работает в своём форке, другая — в основном
   репозитории, обе синхронизируются через несколько remote.
5. **Личные + рабочие аккаунты**: `origin` — рабочий GitHub, `personal` — личный
   GitLab, чтобы не смешивать проекты.
